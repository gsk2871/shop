# Ubuntu 单机部署与维护

适用环境：腾讯云轻量服务器、Ubuntu、2 核 8 GB 内存。服务器顺序构建三个应用镜像，Docker Compose 管理 PostgreSQL、Go 后端、Next.js 官网和 Nginx。构建依赖访问 npm、Go 模块代理和容器镜像源；发布存在维护停机窗口。

## 首次准备

1. 按 [Docker 官方 Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/) 安装 Docker Engine、Buildx 和 Compose 插件，启用 Docker 开机启动。使用支持 `docker compose up --wait` 的当前 Compose 插件。
2. 安装 Git、Python 3、OpenSSL 和提供 flock 的 util-linux。将完整仓库放到 `/opt/shop`；包含两个前端与 shared 目录，不上传本机 node_modules。
3. 腾讯云防火墙开放官网 TCP 80，SSH 端口仅允许管理来源。默认后台绑定服务器回环地址，数据库及应用端口不映射到公网。检查服务器上已有服务，确保 80 和 8000 端口未占用。Docker 端口转发不能仅依赖 UFW 限制。
4. 执行：

```bash
cd /opt/shop
sudo ./scripts/deploy.sh prepare
sudo editor /etc/shop-deploy.env
sudo editor /var/lib/shop/config/config.yaml
```

prepare 不安装软件，不启动服务；生成随机数据库密码及认证加密密钥，已有配置拒绝覆盖。`/etc/shop-deploy.env` 权限为 0600，采用不带引号的 KEY=value 格式，不支持 shell 表达式；修改 WEBSITE_URL 为实际官网地址，例如 `http://服务器公网IP`。此地址在后台构建时写入，改变后须重新部署。

后端配置从仓库的完整 YAML 模板生成，数据库地址改为 postgres，监听 0.0.0.0:8080，使用容器内部网络。默认网络为 172.30.80.0/24；如与服务器现有网络冲突，需要同时修改 Compose 子网及 YAML 的 auth.trusted_proxies。不要把可信代理范围扩大到整个互联网。

默认 cookie_secure=false，仅用于 IP 验收与 SSH 隧道访问后台。配置 COS 后才能上传图片；启用 HTTPS 后改为 true。数据库密码在部署环境文件和后端 YAML 中必须一致；数据库已经初始化后，单改环境文件不会修改数据库账号密码。

## 国家库与持久数据

```text
/etc/shop-deploy.env            部署环境与数据库密码
/var/lib/shop/config/           后端私有配置及认证密钥
/var/lib/shop/postgres/         PostgreSQL 数据
/var/lib/shop/uploads/          历史本地图片
/var/lib/shop/geoip/             IP 国家库
/var/lib/shop/backups/          备份
/var/lib/shop/releases/         成功版本与最近构建记录
```

国家库下载、许可、热更新和回退见 [IP 国家库维护](WHATSAPP_ROUTING.md#ip-国家库维护)。上传解压后的文件后执行：

```bash
sudo chown 10001:10001 /var/lib/shop/geoip/*.mmdb
sudo chmod 640 /var/lib/shop/geoip/*.mmdb
```

在 YAML 中设置 contact.geoip_database_path 为 `/var/lib/shop/geoip/实际文件名.mmdb`。暂不启用时保持空值，使用默认客服。后端容器以 UID 10001 运行，配置文件及持久目录须允许该用户读取；uploads 须可写。配置挂载整个目录，支持原子替换文件后的热加载。

## 构建和首次部署

```bash
cd /opt/shop
sudo ./scripts/build.sh
sudo ./scripts/deploy.sh init
```

单独 build 用于提前检查构建；init 和 update 自身都会构建，正常首次上线直接执行 init 即可，Docker 会复用构建缓存。init 交互读取管理员初始密码，随后顺序构建、等待数据库、停止应用、备份、执行 migration 和 seed、启动应用并等待健康检查。账号默认 admin，首次登录须改密并绑定验证器。初始化失败可修复后重跑 init，已有账号不会重置密码。

成功版本记录在 releases/current，镜像使用时间、Git 提交与进程号组成的标签。构建使用当前工作目录内容，包括未提交改动；正式发布前应确认工作区干净并记录提交。

官网访问 WEBSITE_URL。后台通过本机终端建立 SSH 隧道：

```bash
ssh -N -L 8000:127.0.0.1:8000 ubuntu@服务器公网IP
```

浏览器打开 `http://127.0.0.1:8000`。本地 8000 已占用时，将命令第一个 8000 改成其他空闲端口，浏览器使用同一端口。

## 更新

```bash
cd /opt/shop
git pull --ff-only
sudo ./scripts/deploy.sh update
```

发布脚本不自动拉代码，不自动提交。构建先于停机，构建失败不会停止当前应用。构建成功后停止入口、官网和后端，完成备份后应用迁移并同步权限，再等待所有应用健康；成功后更新 current。期间数据库持续运行。所有维护命令使用同一 flock 锁，避免并发发布与备份。

迁移或启动失败时应用保持停止；脚本不自动运行 down SQL，也不自动用旧镜像连接迁移后的数据库。修正代码或配置后可重跑 update。健康检查验证后端 readyz、官网响应和后台静态入口；上线后还需人工验证登录、图片上传、内容发布和客服分流。

## 状态、日志与备份

```bash
sudo ./scripts/deploy.sh status
sudo ./scripts/deploy.sh logs
sudo ./scripts/backup.sh
```

日志最多保留每个容器 3 个 10 MB 文件。备份目录以时间命名，包含 PostgreSQL 自定义格式转储、配置／国家库／本地图片／版本记录压缩包和部署环境文件；出现 COMPLETE 文件才代表备份完成。独立 backup 不停止服务，数据库转储具有事务一致性，但与文件复制并非同一时点；发布前的备份在应用停止后执行。

备份含数据库密码及认证密钥，仅 root 可读。定期复制到服务器以外的受保护存储；脚本不自动上传、不自动删除备份和旧镜像，需按磁盘空间及保留策略清理。COS 对象不在本地备份中，须独立开启对象备份／版本管理。不要删除仍需回退的镜像和国家库。

## 失败恢复

1. 根据日志判断是否已执行迁移，核对备份中的 release 与 COMPLETE。
2. 优先修复配置或构建问题并重新执行发布。仅当确认数据库兼容时，才可人工切回旧镜像。
3. 如需数据库恢复，停止全部应用写入，使用备份 database.dump 在独立数据库验证 pg_restore；恢复配套配置、全部认证密钥、本地图片及国家库，核对 COS 对象和数据库引用。
4. 确认数据及 schema 与目标镜像一致后，再启动目标版本并验收。恢复数据库会丢失备份之后的写入，不能仅凭脚本错误直接覆盖现有数据库。

## 域名与 HTTPS

当前入口配置用于无域名阶段：官网 80、后台回环 8000，不包含自动申请证书。域名就绪后，将官网及后台域名解析到服务器；准备证书并通过 Compose 覆盖配置挂载证书和生产 Nginx 配置、开放 443。后端及数据库仍不暴露公网。后台 /backend/ 须保留同源代理及 Host、X-Forwarded-Proto；官网入口继续覆盖 X-Client-IP。

完成 HTTPS 后，将 WEBSITE_URL 改为官网 HTTPS 地址、后端 cookie_secure 改为 true，重新构建部署并验证后台登录。证书续期须单独设置，不能只申请一次。
